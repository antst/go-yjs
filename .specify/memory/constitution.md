# y-crdt (Go) Constitution

## Core Principles

### I. Yjs Wire Compatibility (NON-NEGOTIABLE)

This library MUST produce and consume binary payloads that are
byte-for-byte identical to the reference JavaScript Yjs
implementation. Any divergence is a correctness bug, not a
style choice.

- All encoding formats (V1 and V2) MUST match the Yjs reference
  output for identical operations.
- State vectors, update payloads, and delete sets MUST
  round-trip correctly between Go and JavaScript Yjs.
- The sync protocol messages (SyncStep1, SyncStep2, Update)
  MUST interoperate with Yjs clients without adaptation layers.
- Awareness protocol messages MUST interoperate with
  y-protocols awareness implementation.
- Compatibility MUST be verified by generating reference
  payloads in JavaScript Yjs and asserting byte equality in Go
  tests.

### II. Single-Package Library

This is a Go library, not a service. It MUST remain a single
importable Go module with a clean, minimal public API.

- All exported types and functions MUST be usable without
  framework dependencies.
- The library MUST NOT impose transport choices (HTTP, WebSocket,
  NATS) on consumers. Transport helpers, if provided, MUST be
  in a separate subpackage that consumers can import optionally.
- Configuration MUST be via struct fields and functional options,
  not environment variables.
- The library MUST NOT start goroutines that outlive function
  calls unless explicitly requested by the consumer (e.g.,
  awareness timeout cleanup).

### III. Zero External Runtime Dependencies

The library core MUST minimize external dependencies. The CRDT
engine, encoding, decoding, and sync protocol MUST NOT depend
on third-party libraries at runtime.

- Standard library and golang.org/x packages are acceptable.
- Test-only dependencies (mocking, assertions) are acceptable
  in `_test.go` files.
- Deep-copy utilities MUST be replaced with hand-written copy
  logic or generated code if they are the sole external dep.
- Any new runtime dependency MUST be justified in a spec
  clarification and approved before introduction.

### IV. Test-First Development

Tests MUST be written before implementation for all new features.

- Unit tests MUST cover encoding/decoding round-trips for every
  data type and content type.
- Compatibility tests MUST verify Go output against JavaScript
  Yjs reference payloads.
- Edge cases (empty documents, single-client, concurrent edits,
  large documents) MUST have dedicated test cases.
- Benchmarks SHOULD be provided for performance-critical paths
  (encoding, decoding, merge, apply update).

### V. Cross-Language Compatibility Tests

Every encoding format and protocol message MUST have a
corresponding compatibility test that validates against
JavaScript Yjs reference output.

- Reference payloads MUST be generated by a JavaScript test
  harness using the official `yjs` npm package.
- The Go test MUST perform the same operations and assert byte
  equality of the encoded output.
- When adding V2 encoding support, V1 compatibility tests MUST
  NOT be removed or weakened — both MUST pass.
- Compatibility tests MUST cover: state vectors, full document
  updates, incremental updates, delete sets, awareness messages,
  and sync protocol message sequences.

### VI. Root Cause Analysis (NON-NEGOTIABLE)

All debugging and bug fixing MUST be driven by root cause
analysis. Speculative fixes are strictly forbidden.

- Before any fix, the actual root cause MUST be identified and
  documented with evidence.
- Fixes MUST directly address the identified root cause, not
  symptoms.
- For compatibility failures, the investigation MUST compare
  byte-level output between Go and JavaScript Yjs to identify
  the exact divergence point.

### VII. DRY — Single Source of Truth

- No two functions MAY implement the same encoding/decoding
  logic.
- V1 and V2 encoders MUST share common base encoding primitives
  (varint, string, byte array) rather than duplicating them.
- Constants, type IDs, and protocol message types MUST be
  defined in one canonical location.

### VIII. Lint on Completion

Code MUST pass `golangci-lint run` with zero violations before
committing. Linter configuration MUST NOT be bypassed with
`nolint` directives unless justified in a comment.

### IX. No Legacy Code

Dead, deprecated, or unused code MUST be removed. Stub
implementations (like the current V2 encoder placeholder) MUST
be replaced with real implementations or removed entirely — not
left as misleading placeholders.

### X. No Busywork

Every task, test, and artifact MUST deliver demonstrable value.
Do not create documentation, comments, or abstractions "just in
case."

### XI. Meaningful Tests Only

Tests MUST defend real invariants or catch real regressions.
Never write tests for the sake of coverage metrics. Every test
MUST verify either:
- Byte-level correctness against Yjs reference, or
- A specific behavioral contract of the CRDT algorithm, or
- An edge case that has caused or could cause real bugs.

Coverage targets (Principle XIV) set a floor for *how much* new
code is exercised; this principle governs *whether each test earns
its place*. Both apply — neither overrides the other.

### XII. Latest Dependencies Always

Verify latest dependency versions online (pkg.go.dev, GitHub
releases) before adding or updating. Never trust training data
for version numbers.

### XIII. No Assumptions

If the Yjs specification or behavior is unclear, verify against
the JavaScript source code. Do not guess encoding formats,
message structures, or protocol sequences.

### XIV. Test Coverage Floor — ≥95% on New & Touched Code (NON-NEGOTIABLE)

New and changed code MUST reach at least 95% statement coverage,
measured per change via `go test -coverprofile` over the
added/modified lines and the functions containing them.

- This is a FLOOR, not a license to pad. Every test MUST still
  satisfy Principle XI — coverage reached with meaningless tests
  is a violation, not compliance.
- If meaningful tests cannot reach 95%, the uncovered lines are
  either dead code (remove per Principle IX) or MUST be justified
  in the change description and accepted in review. Blanket
  waivers are not acceptable.
- Every bug fix MUST ship a regression test that fails before the
  fix and passes after (pairs with Principle VI).
- **Scope — new and touched code only.** The floor applies to (a) newly added code and (b)
  existing code a change *touches* (the modified lines and the functions containing them).
  Pre-existing code a change does NOT touch is **not (yet)** required to meet the floor — there
  is no retroactive whole-codebase coverage mandate. Raising legacy coverage is encouraged but
  not gated.

### XV. Motivated Edits Only — No Speculative Changes (NON-NEGOTIABLE)

Every edit MUST carry a clear, evidence-based story: WHAT is
changing, WHY it is necessary, and HOW it produces the intended
effect. Edits made in the hope they *might* help are forbidden.

- No guess-and-hope. Changing code to "see if it fixes" an issue,
  without a demonstrated causal link between the edit and the
  problem, is PROHIBITED. This extends Principle VI (root cause
  analysis) from bug fixes to EVERY edit — feature, refactor, or
  fix.
- The what/why/how MUST be statable before the edit is made. If
  any of the three reduces to "I think this might work," stop and
  investigate until it no longer does.
- Fix what you find. A genuine, understood deficiency discovered
  while working on something else SHOULD be fixed, not left
  behind — leaving a known problem in the code is itself a defect,
  and this is NOT a scope violation. The only bar is that its fix
  meet this principle like any other edit, described as its own
  clearly-labeled change (a separate commit where practical).
- Scattershot changes — altering several things at once in the
  hope one helps, without understanding each — are forbidden. One
  understood change beats many hopeful patches.
- A change whose description cannot articulate what/why/how is
  incomplete and MUST NOT merge.

## Encoding Protocol Reference

The Yjs binary protocol defines two encoding versions:

- **V1**: Stable, widely deployed. Uses fixed encoding strategies
  for client IDs, clocks, and content. All struct fields encoded
  with `WriteVarUint` / `WriteVarString` directly.
- **V2**: Optimized for compression. Uses run-length encoding and
  delta-coding for client IDs and clocks. Produces smaller
  payloads for documents with many operations from the same
  client.

Both versions MUST be supported. V1 is the baseline; V2 is
required for production use with Hocuspocus/y-protocols clients
that negotiate V2.

## Anti-Patterns — Quick Reference

1. Do not guess Yjs encoding behavior — verify against JS source
2. Do not add transport/server code to the core package
3. Do not add runtime dependencies without justification
4. Do not leave stub/placeholder implementations
5. Do not skip compatibility tests for new encoding paths
6. Do not apply speculative fixes
7. Do not add comments explaining obvious code
8. Do not create abstractions for hypothetical future needs

## Governance

This constitution supersedes all other practices for the y-crdt
repository. Amendments require documentation of the change, the
rationale, and a version bump.
